# Architecture decisions
1. Retain the active frontend/, backend/app/ and ml/ layout. The nested backend/frontend and backend/backend copies are outside the root launch path. Preserve their contents.
2. Introduce operational contracts under /api/v1 while legacy clients keep /api. Future adapters need independent shape, scope and authorization tests. The same-origin Next API currently provides its own demo identity/data and cannot establish FastAPI authorization.
3. PostgreSQL 16 with pgvector is the intended shared deployment. SQLite is a local fallback. Readiness reports the effective engine. Redis is optional for the local demo. A production deployment must fail closed on loss of its configured tenant database.
4. **Open, privacy review required.** §6.1 permits an unlinkable group registry containing group_id and identity_commitment without user_id. Never persist an identity-to-commitment mapping. §9.2's broader language needs reconciliation across enrollment, reverse proxy logs, backups and verifier services.
5. Keep the three persona previews public, synthetic and read-only. Entry into an existing dashboard follows login. Publishing, scheduling and approved grading changes require backend enforcement.
6. §8 claims ₹400 blended ARPU, but 60% × ₹250 + 40% × ₹450 gives ₹330. Reconcile forecasts before use. §10 gives 1187 → 936 as 23%; the raw change is about 21.1%. All three improvements remain synthetic source claims.
7. Keep existing ML dependencies optional. An installed package capability signals availability for development only. Training, calibrated uncertainty and deployment validation are separate gates.
8. Use configurable institutional attendance thresholds before operational adoption. The existing 75% forecaster reflects a prototype assumption.
9. **Phase 05 — ZK Group Members Privacy Model.** `zk_group_members` stores `(group_id, identity_commitment)` with absolutely NO `user_id`. There is no table, column, or join path that links a user to their identity commitment or nullifier. The enrollment ceremony MUST use a blind-signature protocol so the server never learns which user produced which commitment. `grievance_tickets` uses `nullifier` unique per `(tenant_id, proof_scope)` for double-submit prevention without identity linkage. Infrastructure-level controls (IP logging in reverse proxies/CDN, timing correlation) require separate threat model review before production deployment.
10. **Phase 05 — Append-Only Audit Events.** `audit_events` table is append-only by application policy. Application code MUST NOT UPDATE or DELETE rows. Sensitive routes set `is_sensitive_route=True` which suppresses IP address storage. The audit trail covers auth, grade changes, ticket lifecycle, and all security-relevant actions.
11. **Phase 05 — TTL and Data Deletion.** `grievance_tickets.ttl_expires_at` and `assets.ttl_expires_at` support time-bound retention. Automated purge jobs must be configured per institution's data-retention policy. DPDP-related consent/data-retention policies must be reviewed by institution counsel, not self-certified.
12. **Phase 05 — pgvector 384-dimensional Embeddings.** Document chunks and events store 384-d embeddings (matching all-MiniLM-L6-v2) with ivfflat cosine indexes. SQLite fallback stores embeddings as JSON text. Production deployments MUST use PostgreSQL with pgvector extension for vector similarity search.
